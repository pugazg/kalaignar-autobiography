# இன்றைய குறள் — Daily Kural design

One Kural a day on `/read`, the same one for every reader on earth.

Implemented in `lib/daily-kural.ts` (selection), `components/DailyKural.tsx` (panel) and
`app/read/page.tsx` (placement and cache policy). Tested by `npm run test:daily-kural`.

This document exists because several of the decisions below look like they could be simplified, and
each simplification breaks something that is not obvious from the code alone.

## Algorithm

```
Asia/Kolkata date, "YYYY-MM-DD"
        ↓  FNV-1a, 32-bit
    hash % 1330
        ↓  + 1
    Kural number, 1..1330
```

FNV-1a with offset basis `2166136261` and prime `16777619`, over UTF-16 code units of the date
string. `Math.imul` keeps the multiply in 32-bit space and `>>> 0` keeps the result unsigned.

Properties that matter:

- **Deterministic.** A pure function of the date. No database, no stored state, no runtime
  randomness, nothing per-visitor.
- **Global.** Every reader on a given Indian day sees the same Kural.
- **Stable forever.** FNV-1a is fully specified, so the same date yields the same Kural in any
  language and any runtime, indefinitely. This is the important property: the value is a claim
  *about a date*, and it must not drift because a JavaScript engine changed.

### Why a hash and not `dayOfYear % 1330`

A sequential walk takes 1330 days — three and a half years — to come back around. Most readers
would only ever meet அறத்துப்பால், in printed order, and because the அதிகாரம் changes every ten
Kurals, the subject would change only every ten days. Hashing scatters consecutive days across all
three பால் while staying completely reproducible. The test suite asserts this directly: over four
years, zero consecutive days advance by exactly one, and all three பால் are reached.

### Changing the algorithm changes history

Any edit to the hash, the modulus, the `+ 1`, or the date format silently reassigns **every day's
Kural, past and future**. The test file pins `2026-08-21 → 319` and checks FNV-1a against published
vectors precisely so that such a change cannot pass unnoticed. If you are deliberately changing the
selection, update the pinned expectation in the same commit and say so in the message.

## Timezone

The date is resolved in **`Asia/Kolkata`**, by zone name:

```ts
new Intl.DateTimeFormat("en-CA", { timeZone: "Asia/Kolkata", ... }).format(date)
```

"Today" has to mean one thing worldwide, and for this library that day is the Indian one. A reader
in Toronto at 22:00 sees the same Kural as a reader in Chennai, who is already in the next morning.

**Do not replace this with a manual UTC offset.** India observes no daylight saving and the offset
has not moved in decades, so `+5:30` arithmetic would appear to work — which is exactly why it is
the wrong thing to write. It encodes a fact about the zone's current rules instead of naming the
zone, and it silently produces a wrong date if those rules ever change. Naming the zone stays
correct by definition. `en-CA` is used only because it formats as `YYYY-MM-DD`, sparing a manual
reassembly of the parts.

## Cache behaviour

`/read` is otherwise a fully static page. A statically prerendered page would freeze the daily Kural
at **the build date** — it would then never change until the next deploy, which is the one thing
this feature must not do. So the route declares:

```ts
export const revalidate = 900;   // app/read/page.tsx
```

**The revalidation interval controls freshness only. It does not control rotation.** The Kural
changes exactly once per day, at midnight IST, and that is a property of `getDailyKural`, not of the
cache. The interval only bounds how long after midnight a cached page may still show yesterday's
selection. Raising it to an hour does not make the Kural change hourly; it makes the changeover up
to an hour late. Lowering it costs a little more regeneration of a cheap page.

Verify the setting from the build rather than the route table, which still prints `○ (Static)`:

```bash
node -e 'console.log(require("./.next/prerender-manifest.json").routes["/read"].initialRevalidateSeconds)'
# 900
```

`DailyKural` is a **server component**, passed as an element from `app/read/page.tsx` into the
client-side `LibraryHome` (a client component cannot import a server component, but it can receive
one as a prop). This keeps date resolution on the server: no hydration mismatch, no client clock to
disagree with, and the couplet is present in the HTML for crawlers and Reader mode.

## Source integrity

The panel consumes the released archive through `data/thirukkural.ts`, which reads
`public/data/thirukkural/index.json` and the per-adhikaram files generated by
`scripts/import-thirukkural.mjs` and verified by `scripts/validate-thirukkural.mjs`.

It must never:

- select on the client, or from `Date` as read in the browser;
- use randomness of any kind;
- read Kural text from anywhere other than the generated data;
- introduce a second copy of any Kural or உரை into the codebase.

**Quoted Kurals are not a source.** The edition's front-matter மதிப்புரை essays quote 19 Kurals, and
14 of those 19 use a sandhi that differs from Kalaignar's printed text — reviewers set
`குணமென்னும்` where the edition sets `குணமென்னுங்`. The importer excludes those pages and the
validator proves the exclusion held, so any Kural reached through the generated data is already the
edition's own text. Nothing in this feature should ever reach around that.

The panel preserves the same separation as the full Kural page:

```
திருவள்ளுவர்  →  couplet, both printed lines, never joined
கலைஞர் மு. கருணாநிதி  →  உரை, in its own labelled region
Reader  →  their own reading
```

Nothing here paraphrases, summarises or "explains" either voice. The panel is a way in, not a digest.

## Print behaviour

The global print stylesheet in `app/globals.css` deletes `nav`, `header`, `footer` and anything
carrying `data-print="hide"`.

Therefore the panel:

- sits at the top of `<main>`, **immediately after the banner but outside `<header>`** — inside it,
  the whole panel would vanish from Print → Save as PDF;
- carries **no `data-print="hide"`**; that attribute is for interactive chrome only;
- keeps the Kural number, both printed lines, the உரை, the attribution and the source line on paper.

A printed page that dropped the source line would present the text as if it came from nowhere.

## Accessibility

- Couplet in `<blockquote lang="ta">`, its two printed lines as separate block elements, wrapped
  rows hang-indented so a viewport break cannot be mistaken for one of Thiruvalluvar's line breaks.
- உரை in a region labelled `கலைஞர் உரை`.
- Heading levels: the page's `h1` → `h2 இன்றைய குறள்` → `h3 கலைஞர் உரை`. The உரை heading is an `h3`
  because it belongs to this panel; as an `h2` it would sit in the page outline as a peer of the
  shelves, as though the library had a "கலைஞர் உரை" shelf.

## Testing

```bash
npm run test:daily-kural
```

21 checks: determinism over repeated calls, FNV-1a against published vectors, timezone independence
across the 18:30 UTC boundary in both directions, range across 10 000 dates, rejection of malformed
input, and a four-year distribution check. The distribution check is a **degeneracy** test, not a
uniformity proof — with 1460 draws from 1330 slots repeats are expected; the bounds only catch a
hash that has collapsed to a constant, a short cycle or a stuck bit.

`TOTAL_KURALS` is asserted against the released index rather than trusted as a constant, so the
feature cannot drift from the archive.

## Future extension

English is **not** implemented and should not be added as part of this feature. The archive holds
released English page records, and if an English layer is ever added to the reading room, the Daily
Kural would follow it rather than lead it — the selection is language-independent by construction,
so only the panel's rendering would change. Any such work belongs in its own step, with its own
provenance review of the English text.
